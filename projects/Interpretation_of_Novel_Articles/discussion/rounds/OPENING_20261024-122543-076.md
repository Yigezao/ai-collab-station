# 总管开场

【新需求：UI 易用性改造】

用户原话："感觉UI使用起来还是麻烦，我想要直接浏览选择文件，想要什么操作直接选择操作数（给出说明），我尽量不写代码，接口都留好，清晰明了。每个产出地址，具体检索什么的都写好。"

现状：现有 UI（ui/server.py 生成页面）是"下拉选命令 + 手填参数串/路径"，用户不想查命令、不想手敲路径。本需求属于原方案范围内的 UI 增强，但改动面较大，需要先收敛成 v2 方案再实施。

本轮讨论要解决 5 件事，每人发言给可落地做法与代价，不要泛泛而谈：
1) 文件/目录选择：本地 http UI 中浏览器 <input type=file> 拿不到绝对路径（浏览器安全限制）。请比较并推荐：A 服务端目录浏览 API（仅 127.0.0.1，列盘符/子目录，点选返回绝对路径，可新建目录）；B 上传复制到 data/uploads（会产生副本）；C 桌面 GUI/系统对话框（新增依赖）。必须覆盖 Windows 中文路径、空格、盘符切换、只读浏览边界，默认不引入重量级依赖。
2) 操作即选择：每步可用操作做成带说明的选项（下拉或卡片），选中后显示：做什么、需要哪些输入、必填/可选、默认值来源、会写到哪里、失败情况（退出码含义）。第 1 步现有"参数串"必须拆成结构化字段（search 的关键词/语言/条数等）。
3) 输入自动带出：index.json、variant 目录、audio_manifest.json 等能从上一步产物自动发现的就预填，也可手动选；不让用户记 work_id/variant_id。
4) 产出地址写清楚：执行前显示"将写入 <绝对路径>"，执行后显示实际产物文件/目录，并提供一键打开目录（本地服务可调用系统资源管理器）；禁止静默覆盖，需要 force 的必须二次确认。
5) 检索口径写清楚：Gutenberg search 的 query（书名/作者、繁简限制）、language 取值、条数、返回字段、空结果说明；preflight 依赖检查；各步骤产物清单（script.md/script_lines.txt/manifest.json 等）在页面上可读。

边界与不变量：
- 只改 UI 层与必要说明文档，不改 source/segmentation/script/audio/video 的 CLI 契约、manifest 与退出码。
- 标准库优先；新增第三方依赖要给理由与替代方案，默认不引入。
- 保留现有 CLI 与测试可用；新增能力要有可自动验证的测试（目录浏览 API 的路径校验、免手填路径走完五步、桌面能力不可用时的降级）。
- 不新增联网（除既有 Gutenberg 检索）；UI 仍只绑 127.0.0.1；真实 ffmpeg 编码仍未验证，不得宣称端到端验收通过。

讨论要求：S01 先给整体方案（架构、接口、改动文件、风险、测试点），S02 再给独立评审与补充（重点：A/B/C 选型、路径安全、可用性缺口），最后收敛成 v2 方案交用户批准。本轮只讨论，不写代码。
