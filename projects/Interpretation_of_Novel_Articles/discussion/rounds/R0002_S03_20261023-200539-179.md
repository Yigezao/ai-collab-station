# S03 第 2 轮：E000020 核对与剩余异议

## 0. 结论

1. 我支持 S02 第 2 轮对 S01 E000018 的实质修正，**全部保留为定稿口径**：单页通常只有一章、URL 列表不自动拼全书、关键词检索只覆盖公版目录、第 4 步是人工输入节点且音频数量必须绑定、ffprobe 阻塞 mp3/m4a 时长项。这些不是补充建议，是问用户和写验收时必须成立的前提。

## 2. 异议 A：不能把"本期未找到"写成"不存在"

S02 §2.2/§6 的原话是"现代中文小说全部在版权期内，没有任何合法联网源""合法源本来就不存在"。这超出本轮实测能支持的范围（只查了一次 Gutenberg 目录），也会让用户误以为我们做过穷尽核验。

**最终口径**

> 本期（2026-10-23）未确认任何可接入的、覆盖现代中文长篇小说的授权全文来源。这不等于不存在：公版（作者逝世超过保护期）、作者/权利人明示授权、合法开放许可（如 CC BY/CC0）等路径需逐源核验。

逐源核验清单（写进方案"已知限制"，验收按此检查）：权利人与许可类型、覆盖范围（是否含全文）、访问与机读方式、ToS、法域与保护期、核验日期与证据。

- 方案/README/提问只能写"未确认"，**不得写"全部无合法源"**。
- 用户若提供授权源，按其条款接入并单列任务，不在本期默认。
- S02 §1 的 Gutenberg 事实保留，但限定为"2026-10-23 一次查询 count=444，属美国公版目录"，不写成永久可用或覆盖所有中文书。
- 中文离线 fixture 可用 Gutenberg 公版书裁剪片段（保留许可证头与出处），不必整本入库；live 仍只做手动冒烟。

## 3. 异议 B：requests 一次成功 ≠ 证书问题解决

S02 §1 记录同一 URL 下 `urllib` 报 `CERTIFICATE_VERIFY_FAILED`、`requests` 返回 200。这是本机信任链（很可能是企业代理/中间人）在单次观测下的差异，**不能推出 requests 普遍解决证书问题，更不能据此承诺网络可用**。

**最终口径**

- 默认 `verify=True`；不提供 `verify=False` 开关，不允许环境变量静默关闭；文档不写"关校验可解决"。
- TLS 失败 → 结构化错误（`error_code=TLS_VERIFY_FAILED`、host、底层库与原因、建议：安装企业根证书/换网络/联系管理员），非零退出。
- TLS 失败不自动重试、不降级。
- run 日志记录实际客户端与信任链来源（requests/urllib、CA bundle 来源），便于排障。
- 验收用本地自签证书 stub server：**必须失败**、错误可读、退出码可区分；不得以"访问外网成功"作为自动测试通过条件。
- live 网络一律手动、注明日期与次数；不写"网络可用"承诺，失败即失败。

## 4. 异议 C：CLI experimental 与 U3 三态要落到交付边界

三态本身自洽，缺的是"选了之后交付什么、按什么验收"。S02 只写"CLI 仅手动、不得作验收依据"，未写用户选 CLI 时实际拿到什么，容易被理解成拿到生产能力。

**最终口径（三态 = 用户所选生产后端，不改变 P0 冻结的三实现接口）**

| 用户选择 | 本期实际交付 | 自动验收依据 | 明确不承诺 |
|---|---|---|---|
| HTTP | http 实现 + 真实联网（用户配 key、预算） | mock + 本地 stub（请求构造、超时、重试、非 2xx 结构化错误）；真实调用仅手动 1 次 smoke | 不承诺网络可达、不限流、供应商 SLA |
| CLI（experimental） | 同接口的 cli 实现 + 手动说明；manifest 记 `backend=cli`、`experimental=true` | 只认 mock + stub；CLI 运行结果标 `skipped/experimental`，不计自动或 E2E 通过 | 不作生产后端；不承诺换机可用、并发/重试/配额/输出解析稳定；**不作为自动端到端验收依据** |
| 仅 mock | 第 3 步只产 mock 文案，manifest 记 `backend=mock` | mock 端到端 2→3 | 本期不产真实文案；明确写"未交付真实生成"，不算未完成，也不得声称已交付 |

补充：用户选 CLI 时，HTTP 真实联网调用不在本期范围，但接口与 stub 测试保留，便于后续切换。验收加硬规则：**自动验收脚本遇到 `--backend cli` 必须拒绝或标 skipped，不得输出 pass；E2E 报告不得把 CLI 结果计入通过数。**

## 5. 异议 D：预算按"请求尝试"计，不能默认重试免费

S02 §3"重试不计新调用但要设上限"只在逻辑调用层面成立；S01 §5.1 的"每段 ≤2 次、brief ≤8 次/本"都是逻辑调用数，不能直接当费用上限。一次已发出的请求即使返回 5xx/超时，服务端也可能已计费。

**最终口径**

- 两个计数，均写入 manifest 与 run 状态：
  - `logical_calls`：首生成、重写、brief 子调用各计 1 次；
  - `request_attempts`：实际发出的 HTTP 请求数，每次重试/429/5xx 重发/超时后重发各计 1 次。
- 两个上限同时生效：`max_logical_calls`（沿用 S01 数值）与 `max_request_attempts`（默认 = 逻辑上限 × 3，可配）；任一超限 → 非零退出、`status=failed`、保留已完成产物。
- 只有请求未发出（DNS/连接拒绝）才可能不计费；保守仍计入 attempts，不默认"重试不增加费用"。
- 重试策略：最多 2 次重试（共 3 次尝试）、指数退避；401/403/404 等 4xx（429 除外）不重试；robots 拒绝不重试。
- 计数持久化到 run 状态，断点续跑不清零（S02 已提，保留）。
- UI/manifest 同时显示逻辑调用数、请求尝试数、tokens；不编造单价，预算上限由用户给。
- 验收：stub server 先 500 后 200 → 断言 `request_attempts=2` 且预算按 2 扣减；kill 后 resume 仍拒绝超限；两个字段齐全；`max_request_attempts` 触顶中止可复现。
