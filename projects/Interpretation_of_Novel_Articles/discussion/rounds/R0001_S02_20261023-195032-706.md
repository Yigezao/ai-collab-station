# S02 第 1 轮发言：模块边界、关键依赖与可验收性审视

## 0. 结论先行

S01 的大方向我同意：合法来源硬约束、CLI 优先 + 产物契约、UI 只做壳、章节解析前置、第 4 步只占位、第 5 步用 ffmpeg 子进程。但现稿有 **4 处在实施时会直接返工**，建议在 P0 契约冻结前修正：

1. **book_id 单层身份与"多版本对比"自相矛盾**：同一本书两个版本前 2k 字不同 → 两个 book_id，第 1 步"保留较优版"无处比较；正文一改、id 就变，下游引用断。必须两级身份。
2. **串联逻辑只写在 UI（S01 4.3）**：导致"多步骤串联"没有无头可验收实现，CLI 用户拿不到批量能力，且编排逻辑两份迟早不一致。
3. **相似度指标没有归一化口径**：LCS/8-gram 写成了数字，但"按什么文本、怎么归一、分母是谁"未定义，指标不可复现，阈值等于拍脑袋。
4. **ffmpeg 当前不在本机 PATH，方案里没有 preflight**：P4/P5 会在验收时才爆，而不是开工前暴露。

以下逐项给出修正建议与可执行验收口径。

## 2. 产物契约：不同意按现稿定稿，需三处修正

### 2.1 身份模型必须两级：work_id / variant_id

现稿 `book_id = slug(书名)-hash8(规范化全文前 2k 字)` 的问题：

- 同一本书的版本 A、B 前 2k 字不同 → 两个 `book_id` → 第 1 步的"多版本校验、保留较优"**没有共同的容器**可比、可选。
- 用户重解析、手工改一处错字，`book_id` 就变，第 2/3 步已产出的 manifest 全部指向旧 id。
- 与需求 1"输入多个小说名称、对多个版本校验对比"直接冲突。

修正建议：

- `work_id = slug(规范化书名)-hash8(规范化书名+作者)`：身份来自**名义书**，用户可给 `alias` 覆盖；同一 book 的多个下载共用它。
- `variant_id = sha256(原始文件) 前 12 位`：每个下载/每个来源一个 variant。
- 布局：`data/library/<work_id>/source/<variant_id>/`（原始文件 + provenance），`normalized/` 存**被选中** variant 的产物，`selection.json` 记录选了哪个、评分、是谁选的（规则/用户）。
- 这样"多版本对比"是在 work 级别比较 variant，选中的结果可留痕、可回滚。

### 2.2 manifest 缺关键字段，验收会靠"看日志猜"

建议每个 manifest 增加：

- `status`: `ok | failed | needs_review`（失败也落 manifest，UI 才有结构化错误可展示）
- `inputs` 每项带 `sha256`：重跑时输入没变就跳过，这是"断点续跑/幂等"的唯一依据
- kind 专属必填字段：`segment.chapter_range / char_count`、`script.estimated_seconds / similarity`、`audio.duration`、`video.duration/resolution/fps`
- `pipeline_run_id` + `parent_artifact_id`：UI 串联追溯、"只重跑某一段"都依赖它

落地方式：**每个 kind 一份 JSON Schema**，`common/manifest.py` 负责校验，测试覆盖合法/非法样例。只有 schema 校验测试通过，"契约定死"才不是口号。

### 2.3 artifact_id 不要用生成序号

`seg:003` 是生成顺序；重跑、插段、从一个 start-chapter 重来都会漂移，目录名与 id 会失配。建议用章节范围：`seg_c0001-0010`，目录同名，一张映射表都不要。

## 3. 来源检索：把"合法"与"可验收"同时落到细节

- 语义同意 S01："多书名 → 多资源"的批处理。但**需求字面是"关键词检索"**，验收口径建议写成：在合法源内按书名检索 → 返回候选列表（标题/作者/来源/license）→ 规则或用户选中 → 下载。这样"检索"真实存在，又不引入盗版站。需 D1 由用户确认。
- **P1 范围收窄**：只做 Gutenberg（gutendex 检索 + epub/txt 下载）+ 本地导入；中文维基文库挪 P2。理由：中文公版覆盖薄、MediaWiki 的章节结构与 txt 差异大，现在做等于开第二个抓取工程，拖住主链路。
- 网络测试默认跳过（标记 live，手动执行，结果贴进 handoff），CI 只跑录制 fixture。否则"不编造测试结论"这条我们自己先破。
- **多版本评分要可复现**：乱码率 = 替换符/控制字符占比；章节一致性 = 解析章数 / 标称章数；正文占比 = 正文行 / 总行。每项公式、权重、阈值区间写进 README，并用 2–3 个构造 fixture（一个截断、一个乱码、一个完整）断言排序结果。"质量较好"不能只靠人眼看。
- provenance 补字段：`robots_decision`、`http_status`、`fetched_at`、`license_url`。D 类（用户 URL）即使二期不做，字段先留。

## 4. 章节解析：同意放第 1 步，但必须是独立可跑子命令

- 同意 S01：解析归 novel_capture，理由（多版本评分依赖章节结构）成立。
- 但"各文件夹独立"的准确边界要写进方案：**功能包之间只通过「文件 + CLI + manifest」交互，禁止互相 import 业务代码**；数据依赖（segmenter 读 `chapters.json`）允许。用一条 import 扫描测试固化：`common` 不得 import 任何功能包，功能包之间互不 import。
- `chapters.json` 缺失或置信度低时，segmenter 的行为要定死：报错并提示先跑第 1 步，不要隐式回退；同时提供 `parse --book <work_id> --override chapters_override.json`，让用户能手工救。否则第 2 步的"独立运行"是假的。

## 5. 截取：1/3 规则同意严格大于，补两个定义

- **"字数"的口径**：以归一化后正文计（去空白、不算章节标题）还是含标题？必须写死并配 fixture，否则边界测试没有意义。建议：正文汉字+标点计入，章节标题不计。
- **目标字数的口径**：`--target-chars` 表示本段正文累计（不是从书首累计）；段间默认不重叠（`--overlap 0`）。第 5 步要逐段成片，重叠会造成剧情重复，重叠应列二期。
- 每段 manifest 必须写 `chapter_range` + 首末章标题，第 3 步要靠它"不脱离背景"。

## 6. 文案生成：指标可复现，LLM 可替换

### 6.1 相似度校验（现稿不可复现）

- 归一化：去空白/标点、全半角统一、数字统一；对比对象默认"本段原文"，另报全书口径。
- 8-gram 重合率 = 文案中命中原文的 8-gram 集合 / 文案 8-gram 集合（去重）。
- LCS 建议默认 16 字（可配 12–24），"20"偏严但对中文不算错，关键是把默认值、归一化、对比对象写进 README 并由 fixture 锁定。
- "超阈值重写一次"要把两次指标都写进 manifest；`needs_review` 时必须给出**超标的上下文定位**（哪一句、哪 16 字），否则用户无法修。
- 用 3 条构造 fixture（原文照抄 / 改写 / 原创）锁定阈值可行性；没有 fixture 的阈值就是拍脑袋。

### 6.2 LLM 依赖（D3）

- 本机已有 claude/codex CLI → 建议定义 `LLMBackend` 接口，两个实现：本地 CLI（零 key、用户已登录环境）与 HTTP API（可配）。默认本地 CLI，无 key 不阻塞开发。
- 测试一律录制回放（fixture JSONL），manifest 记录 model / prompt_hash / 输入摘要 hash；测试不联网。
- 全书 brief 用分段 map-reduce，预算写明（如 ≤ N 次调用/本）；缓存 key = 书内容 sha256 + prompt 版本。

### 6.3 文案形态

- `script_lines.txt` 一行一句要加硬约束：**单行 ≤ 40 字**，按句末标点切（TTS 断句友好）。验收检查行长分布，而不是只看"文件存在"。
- `estimated_seconds = 字数 / 语速（可配 4.5 字/秒）`。第 4 步未实现时，这是唯一可核对的时长口径，必须进 manifest。
- srt / 剪映草稿同意维持二期。

## 7. UI 集成：串联逻辑不能只活在 UI 里

- 现稿 4.3 把串联放在 UI 侧顺序调 CLI。后果：**"多步骤串联"没有任何无头可测实现**；CLI 用户拿不到批量能力（需求明确要求"每个功能都能单独运行并产出结果"）；编排逻辑两份，迟早不一致。
- 修正：新增 `pipeline/` 包，提供 `run --chain 2,3,4,5 --work <id> --params chain.yaml`，负责按 manifest 串联、失败即停、断点续跑、写 `pipeline_run` 记录；UI 调它、展示进度。P5 的端到端验收跑 pipeline CLI，不依赖点界面。
- **进度契约**：各 CLI 统一写 JSONL 到 `logs/run_<id>.jsonl`（stage/progress/message/artifact），UI 轮询该文件，不解析人读日志。
- streamlit 未安装：方案要写版本约束与安装步骤；UI 只绑 127.0.0.1（与站点一致）。
- 路径：工作区含 `#` 和中文，subprocess 一律用列表参数不经 shell；端到端要拿一个含中文+`#` 的临时目录跑一遍。
- 书库"删除"改为移入 `trash/` 并二次确认，不物理删除用户资料。

## 8. 第 5 步与 ffmpeg：先 preflight，再谈验收

- 事实：ffmpeg/ffprobe 不在 PATH。方案必须包含 `python -m tools.preflight`（或 `common.doctor`）：检查 ffmpeg/ffprobe 版本、可写临时目录、控制台 UTF-8、字体；缺失时给安装指令（winget/scoop）并拒绝运行第 5 步，而不是抛栈。
- **不随项目打包 ffmpeg**（体积 + GPL 分发问题），文档写清安装；验收留 preflight 实际输出。
- 裁剪默认策略同意（视频长→裁尾；音频长→裁尾），但必须显式 `--trim-policy`，manifest 记录实际裁剪区间，用户可复现。
- 图片模式：N 张图，每张 = 音频时长 / N，余数毫秒补到最后一张（简单、可复现，不累积误差）；统一缩放裁剪。
- 复杂滤镜走 `-filter_complex_script` 文件，绕开命令行转义；自检用 ffprobe：时长误差 ≤ 0.5s、音视频流存在、分辨率/帧率符合参数。

## 9. 建议直接写进任务卡的验收项

1. 每个功能包 `python -m <pkg>.cli --help` 可跑，fixture 冒烟离线通过。
2. 每个 artifact kind 的 JSON Schema 校验测试（合法/非法各 ≥2）。
3. import 边界测试：`common` 不 import 功能包，功能包互不 import。
4. 1/3 规则表驱动 ≥8 例（恰 1/3、±1 字、单章超长、末段不足、目标小于单章、章数不足…）。
5. 相似度 3 条 fixture 阈值断言 + 归一化单测。
6. UI 冒烟：能启动、调一个 CLI、展示进度 JSONL（可测 UI 函数，不强依赖浏览器）。
7. 端到端：公版书 1→2→3(mock LLM)→外部音频→5，ffprobe 时长误差 ≤0.5s；同时跑通 pipeline CLI 无头版本。
8. preflight 输出留档。

## 10. 对 D1–D10 的立场 + 新增 D11–D15

- D1 来源边界：**同意**（需用户确认；检索语义按第 3 节落地）。
- D2 `common/`：**同意共享**，但只限契约/IO/子进程封装，用 import 测试固化。
- D3 LLM：**同意必须定**；建议默认本地 CLI 后端 + 可配 HTTP，录制回放测试。
- D4 章节解析：**同意放第 1 步**，但拆成独立 parse 子命令。
- D5 1/3 规则：**同意严格大于**；补"字数口径"与"默认无重叠"。
- D6 library 按书：**同意**，但必须两级身份（work/variant + selection.json）。
- D7 Streamlit：**同意**（未装，写好安装步骤）；串联实现下沉 pipeline 包。
- D8 视频参数：**同意 ffmpeg 子进程**；补 preflight、不打包、复杂滤镜脚本化。
- D9 文案格式：**同意** md + 单行 txt，加 ≤40 字硬约束与 estimated_seconds。
- D10 第 4 步占位：**同意**，但 UI 第 4 步要能接收外部音频并交给第 5 步。

新增，建议在 P0 前定：

- **D11 两级身份**：work_id / variant_id + selection.json（影响所有 manifest 与目录）。
- **D12 编排下沉**：pipeline CLI 为唯一串联实现，UI 只做壳与展示。
- **D13 相似度口径**：归一化规则、对比对象、分母、阈值 fixture。
- **D14 LLM 后端接口**：本地 CLI 默认、HTTP 可配、录制回放。
- **D15 ffmpeg 策略**：preflight、不打包、复杂滤镜用脚本文件。

## 11. 风险补充（按返工概率排序）

1. **D11 不定就写 P0** → 第 1 步多版本对比无处落地，契约全体返工。
2. **D12 不定** → "串联"只能靠人点 UI 验收，CLI 用户缺批量能力，需求"每个功能可单独运行"打折。
3. **ffmpeg 缺失 + 无 preflight** → P4/P5 到验收才炸，且用户装不上时无自助路径。
4. **streamlit 未装 + 中文/`#` 路径** → UI 冒烟要早跑，别留到最后。
5. **LLM 成本/不可复现** → 靠录制回放与 manifest 记录，不靠"相信模型稳定"。
6. **相似度阈值无 fixture** → 指标看着严，实际不可解释、不可调。

## 12. 给总管的建议

P0 只做三件事：目录骨架、**含 D11/D12 的 manifest schema**、preflight 与 import 边界测试。这三件不先定，P1–P4 并行开发必产生接口不一致，返工成本远高于先花半天写 schema 与样例。
