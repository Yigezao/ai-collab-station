# 第 1 轮 S01：整体架构、合法来源边界与关键决策

# S01 第 1 轮发言：整体架构、来源边界与关键决策

## 0. 结论先行

1. **合法来源是硬约束，必须先定再写抓取代码**：只做「本地导入 + 公版书 + 用户授权来源」的适配器，不内置盗版站抓取。否则需求 1 的交付物本身就是风险，也无法写进验收标准。
2. **架构采用「产物契约 + CLI 优先 + UI 只做壳」**：5 个功能文件夹各有独立 CLI 和落盘产物；UI 通过子进程调 CLI 串联，不重复实现业务逻辑。这样同时满足"每个文件夹能单独跑"和"UI 串联"。
3. **章节解析是隐藏难点，应放在第 1 步产出**：多版本质量对比本来就要靠章节结构打分，第 2 步只消费 `chapters.json` 做切分。
4. **第 3 步必须做「全书故事状态 + 防雷同校验」**，否则"不脱离长篇背景"和"不能与原文一样"都无法验证，只能靠嘴说。
5. **第 4 步只留接口占位，不做假音频**；第 5 步用 ffmpeg 子进程，不引 moviepy。

## 1. 合法来源边界（最高优先级，需用户拍板）

### 1.1 事实与风险

- 从任意"免费小说网站"批量抓全文，多数站点内容是盗版，抓取与存储都有侵权风险；技术上还高度依赖对方页面结构，反爬、封 IP、改版会让第 1 步长期不稳定。
- 需求原文"从网上捕获小说资源"若按字面做成通用爬虫，等于把法律风险内置进产品，且无法给出可验证的验收口径。
- **结论：来源能力做成可插拔适配器，默认只装合法来源，不随项目交付任何盗版站适配器。**

### 1.2 建议的四类合法来源（按优先级）

| 类别 | 例子 | 说明 | 建议 |
|---|---|---|---|
| A 本地导入 | 用户已有的 txt / epub | 最可靠、零网络、零法律风险 | 必做，默认路径 |
| B 公版书 | Project Gutenberg / gutendex API；中文维基文库 MediaWiki API；作者逝世满 50 年的中文小说 | 有稳定 API，可检索、可批量 | 必做，作为"联网捕获"主力 |
| C 明确授权/开放 API 的站点 | 站点条款允许或提供 API 者 | 逐站点确认 ToS，写入 `sources.yaml` 的 `legal_basis` | 按需，先不做 |
| D 用户提供 URL + 显式确认 | 用户自己给出的链接 | 只做单页正文提取，由用户确认有权使用，记录 provenance | 可选，二期 |

### 1.3 工程约束（写进验收）

- 每个 adapter 声明：`source_id / legal_basis / 是否支持检索 / 限速 / 所需凭据`，在 `sources.yaml` 中可启停。
- 遵守 robots.txt（`urllib.robotparser`），默认 1 请求/秒，重试 + 指数退避；不绕登录、付费墙、DRM、验证码。
- 不保存任何账号密码，凭据只从环境变量读。
- 每本书写 `provenance.json`：来源、URL、抓取时间、license、adapter 版本。
- 若用户坚持"任意小说站"，应作为高风险项由总管在方案中显式列出并取得确认，而不是默认实现。

### 1.4 "关键词检索 + 空格分隔多书名 + 批量"的落地语义

- 实际语义是"多书名 → 多资源"的批处理，不是通用搜索。CLI 建议：`fetch "书名A 书名B" --source gutenberg --out data/library/`。
- 公版源通常一本书只有一个版本，"多版本校验"在 B 类基本无用武之地；真正需要比较的是 A 类（用户给了两个 txt）和 D 类。所以**版本对比应设计成通用后处理**，不只对抓取生效。

## 2. 模块拆分

### 2.1 目录（按功能命名，英文短名 + 中文说明）

```
Interpretation_of_Novel_Articles/
  README.md
  requirements.txt
  config/default.yaml
  common/                 # 只放契约与基础设施，不放业务
  novel_capture/          # 需求1 捕获
  chapter_segmenter/      # 需求2 截取
  script_writer/          # 需求3 文案
  voiceover/              # 需求4 配音（占位，不实现）
  video_composer/         # 需求5 合成
  ui/                     # 5 步 UI + 串联
  tests/                  # 跨模块端到端
  data/library/           # 运行时产物（不入库）
```

每个功能文件夹含：`README.md`（输入/输出/参数/示例）、`cli.py`、`core.py`、`tests/`。

### 2.2 关键取舍：`common/` 只放契约

"独立"我理解为**能单独运行、不 import 其他功能文件夹的内部实现**，而不是"零共享代码"。`common/` 只允许放：

- `manifest.py`（产物契约读写）
- `paths.py`（library 布局、book_id 生成）
- `logging.py`、`ffmpeg.py`（探测与封装）
- `textio.py`（编码探测、UTF-8 归一）

业务逻辑一律留在各自文件夹。若坚持零共享，代价是 5 份重复契约代码，集成时更容易不一致。**这一项需要表决。**

### 2.3 产物契约（最重要，必须最先定死）

每个阶段的产物 = 数据文件 + 同目录 `*.manifest.json`：

```json
{
  "schema_version": 1,
  "artifact_id": "book:xxx:seg:003",
  "kind": "book | segment | script | audio | video",
  "producer": "chapter_segmenter",
  "created_at": "2026-10-23T20:00:00+08:00",
  "inputs": ["data/library/<book_id>/segments/seg_002.md"],
  "params": {"target_chars": 8000, "rule": "one_third"},
  "files": {"text": "seg_003.md", "meta": "seg_003.json"},
  "provenance": {"source_id": "local_import", "url": null, "license": "user-provided"}
}
```

- 下游只读 manifest，不靠文件名猜。
- `book_id = slug(书名)-hash8(规范化全文前 2k 字)`，保证同一本书跨步骤稳定定位。
- library 按书组织，便于跨步骤复用：

```
data/library/<book_id>/
  source/       原始文件 + provenance.json
  normalized/   book.txt, chapters.json, book_meta.json
  segments/     seg_001.md + .json
  scripts/      seg_001.script.md + .json
  audio/
  video/
```

## 3. 各模块要点与隐藏难点

### 3.1 novel_capture（需求 1）

- 输入：书名列表 / 本地文件 / URL；输出：规范化 `book.txt` + `chapters.json` + provenance。
- 编码：UTF-8(BOM) / GBK / GB18030 / Big5 探测，失败按 GB18030 兜底，统一转 UTF-8。
- epub：zipfile + OPF spine 顺序 + XHTML 正文提取，保留章节标题。
- **章节解析放这里**，理由：多版本对比必须靠章节完整度、乱码率、与标称章节数是否一致来打分；第 2 步只读 `chapters.json`。
- 章节识别：`第[零一二三四五六七八九十百千0-9]+[章回节卷]`、`Chapter N`、`楔子/序章/尾声`、标题独占行。输出带置信度；低于阈值**报错并提示写 `chapters_override.json`**，绝不静默把整本当一章。
- 质量评分（可测）：`w1*章节结构完整 + w2*(1-乱码率) + w3*与标称章数一致 + w4*正文占比 + w5*书名作者匹配`；默认权重可配。
- 抓取缓存到 `cache/`，重跑不重复下载。

### 3.2 chapter_segmenter（需求 2）

- 两种模式：`--target-chars N` 或 `--chapters-per-segment K`；可加 `--start-chapter`、`--overlap`。
- **1/3 规则精确语义（需确认）**：
  1. 按章累加字数，直到累计 ≥ 目标；
  2. 定位目标字数落在哪一章、在该章的相对位置 r；
  3. `r > 1/3` → 该章计入本段；`r ≤ 1/3` → 留给下一段；
  4. 任何情况不切章；单章超长也整章输出；每段至少 1 章；
  5. "超过 1/3"建议按**严格大于**，写进 README。
- 必须配表驱动单测：恰好 1/3、刚过、刚不到、单章超长、章数不足、末段不足。

### 3.3 script_writer（需求 3）

三件事缺一不可：

1. **全书背景摘要**（一次性、可缓存）：从整本书抽 `book_brief`（人物、关系、主线、世界观、基调），这是"不脱离长篇背景"唯一可落地的手段。
2. **滚动故事状态** `story_state.json`：每段生成后更新（剧情推进、人物状态、未回收伏笔），下一段作为上下文；支持从中间段开始生成。
3. **防雷同硬校验**：生成后与原文比对
   - 最长公共子串 ≤ L 字（建议 L=20）
   - 8-gram 重合率 ≤ R（建议 5%）
   - 连续引用占比 ≤ Q
   超阈值自动重写一次，仍超标标记 `needs_review`，不静默通过。

- 文案形态：`script.md`（段落）+ `script_lines.txt`（一句一行，便于粘贴进剪映等 TTS）；长度按"目标时长 × 语速 4–5 字/秒"反推。
- **LLM 依赖是硬决策**：用哪家 API、谁付费、key 怎么放（环境变量，`.env` 不入库）、无 key 时是否降级。不确认无法开工。

### 3.4 voiceover（需求 4）

- 按需求不实现。只建文件夹 + README 写清输入输出契约 + CLI 明确返回"未实现"。
- 不生成假音频。第 5 步支持直接导入外部音频，链路不断。

### 3.5 video_composer（需求 5）

- ffmpeg/ffprobe 子进程，不引 moviepy（重、慢、Windows 易出问题）。
- 视频模式：读音频与视频时长；差异超阈值时用户选"裁视频 / 裁音频 / 指定入出点 / 补静音"。默认策略需写死（建议：视频长→裁尾部；音频长→裁音频尾部）。
- 图片模式：N 张图，每张 `音频时长 / N`，余数毫秒补到最后一张（或均摊，需定）；统一缩放裁剪到目标分辨率；静态图先行，慢推镜头列为可选增强。
- 用 ffprobe 自检：时长误差 ≤ 0.5s、音视频流存在、分辨率/帧率符合参数。
- 批量：音频列表 → 一批视频，命名可追溯。

## 4. 用户流程（UI）

### 4.1 原则：UI 是壳，CLI 是腿

每个按钮 = 用参数调对应 CLI 子进程，读日志与 manifest 展示。好处：单文件夹可单独跑、UI 不重复业务、长任务不卡 UI。

- 选型建议 **Streamlit**（纯 Python、上传/预览方便、迭代快）；Gradio 次选；React 过重。
- 长任务必须 `subprocess.Popen` + 日志文件 + 轮询刷新，不能同步阻塞。

### 4.2 页面

1. **书库**：已捕获书目（书名、章数、字数、来源、质量分），可删除、可重解析。
2. **步骤 1**：粘贴多个书名 / 上传文件 / 选来源 → 运行 → 进度日志 → 多版本对比表（打分，可手动指定保留哪版）。
3. **步骤 2**：选书 → 选模式（按字数/按章数）→ 预览第 1 段章节目录 → 批量生成 → 段落列表。
4. **步骤 3**：选段（可多选）→ 设目标时长/风格 → 生成 → 并排预览原文摘要 / 文案 / 相似度指标 → 导出。
5. **步骤 4**：占位，"暂未实现，可上传外部音频"。
6. **步骤 5**：选素材（素材库浏览/上传）→ 选音频（产物或上传）→ 模式（视频/图片）→ 裁切策略 → 生成 → 预览 + 下载。
7. **串联**：选步骤链（如 2→3→4→5）→ 设参 → 一次跑完，输出多段；每段可见、可重跑、可中断续跑。

### 4.3 串联实现

UI 端顺序调 CLI，把上一阶段 manifest 的输出路径交给下一阶段；失败即停并保留已完成产物。不做"内存里传对象"，保证断点续跑与可复现。

## 5. 分阶段范围（建议）

- **P0 契约**：目录骨架、manifest schema、`common/`、config、README、测试入口。无业务逻辑。**先做，防止并行开发接口不一致。**
- **P1 捕获+解析**：本地导入、编码/章节解析、多版本评分、公版 adapter（至少 Gutenberg）、provenance。UI 第 1 步。
- **P2 截取**：1/3 规则 + 表驱动测试。UI 第 2 步。
- **P3 文案**：背景摘要、滚动状态、相似度校验、mock LLM 测试。UI 第 3 步。
- **P4 合成**：ffmpeg 视频/图片两模式、时长裁剪、ffprobe 自检。UI 第 5 步。
- **P5 串联与端到端**：串联页 + 公版书真实样例全链路（1→2→3→外部音频→5）。
- 第 4 步全程只保留占位。

## 6. 需要拍板的决策

- **D1 来源边界**：接受"不内置盗版站抓取，联网只做公版/授权源，主力本地导入"？（**必须用户确认**，直接影响需求 1 的字面范围）
- **D2** `common/` 共享契约 vs 5 份完全独立代码 —— 我主张共享。
- **D3** LLM 供应商、付费方式、key 管理，以及无 key 时降级行为。
- **D4** 章节解析归属第 1 步（我主张）还是第 2 步。
- **D5** 1/3 规则边界（严格大于）与单章超长处理（整章保留）。
- **D6** 产物目录按书组织 library（我主张）还是按批次 runs。
- **D7** UI 技术栈 Streamlit（我主张）。
- **D8** 视频默认参数（分辨率/帧率/编码）与裁剪默认策略。
- **D9** 文案输出格式（md + 一句一行 txt；srt / 剪映草稿建议二期）。
- **D10** 第 4 步确认仅占位。

## 7. 主要风险

1. **法律/ToS（最高）** → 靠 D1 解决。
2. **抓取不稳定/反爬** → 缓存、限速、优先有 API 的公版源；网络测试用录制 fixture，不在测试中打真实站点。
3. **章节识别失败** → 置信度 + 人工 override + 明确报错。
4. **文案雷同** → 硬指标校验，不通过不交付。
5. **LLM 成本与不可复现** → 模型/参数写入 manifest；测试全 mock。
6. **ffmpeg 缺失、Windows 中文路径/控制台编码** → 启动自检、全程 pathlib + UTF-8。
7. **UI 长任务阻塞** → 子进程 + 轮询。
8. **范围膨胀**（5 模块 + UI）→ P0~P5 分阶段，每阶段可验收。

## 8. 验收口径

- 单元测试：表驱动、无网络、固定 fixture。
- 冒烟：每个文件夹 CLI 能独立跑通最小样例。
- 端到端：公版书样例全链路，产物与 manifest 齐全，ffprobe 时长在容差内。
- 不编造：任何"抓取成功率/相似度"结论必须附实际运行输出。
