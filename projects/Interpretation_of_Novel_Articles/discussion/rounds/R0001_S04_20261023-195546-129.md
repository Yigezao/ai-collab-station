5. **建议总管本轮结束就出裁决 + 用户确认清单**，不必开第二轮；只有用户选"任意站点抓取"或推翻版权/阈值口径时再开。

## 2. 需求 1：把"捕获"拆成四段，每段单独可验收

现行讨论把需求 1 当一个模块谈，验收会糊。建议拆成 **discover → fetch → normalize/parse → score/select** 四段，每段有 CLI 子命令与 fixture。

### 2.1 discover（检索/候选）

- 合法目录内按书名/作者检索：`capture search "Pride and Prejudice" --source gutenberg --json`，返回候选（title/author/language/source/license/下载地址）。
- "多个书名空格分隔"的输入语义要定死：用户明确要求空格分隔，按此做默认；但英文书名与系列名会含空格（`Pride and Prejudice`），必须有 `--names-file`（一行一本）与引号写法，并在 README 写明"含空格书名请用文件或引号"，否则会切错。
- 检索范围：P1 只有 Gutenberg 目录；中文站不在 P1（见 §1）。"关键词检索"在 P1 的真实含义是"公版目录内按书名/作者检索"，方案里要这么写。

### 2.2 fetch（下载）

- 输入候选 → 下载 txt/epub → `work_id/source/<variant_id>/` + provenance。
- 必须有：缓存（同 URL 不重复下载）、sha256、robots/ToS 记录、限速与退避、失败隔离（批处理中一本失败不中断其余，退出码汇总）、部分下载检测（content-length 与落盘大小比对）。
- 不保存登录态、不绕验证码/付费墙/DRM。

### 2.3 normalize/parse

- 编码探测（UTF-8/BOM、GBK、GB18030、Big5）；epub 用 `zipfile` + OPF spine，不引 ebooklib（未安装，也不必装）。
- **输出口径**：原始文件原样保留；规范化产物固定为 `book.txt`（UTF-8 无 BOM）+ `chapters.json` + `book_meta.json`。需求说"格式为 txt 或 epub"是可接受的输入/输出形式，不必反向生成 epub；这一点写进方案，避免验收时争"为什么没有 epub 输出"。
- 章节解析：`capture parse --work <work_id> --variant <variant_id> [--override chapters_override.json]`，独立可跑（同意 S02 的修正）。低置信度报错，不静默整本当一章。

### 2.4 score/select（多版本对比）

- 两级身份：`work_id = slug(书名)-hash8(书名+作者)`（可 alias 覆盖），`variant_id = sha256(原始文件)[:12]`；`selection.json` 记录选中 variant、评分、选择者（规则/用户）、时间。
- 评分公式与权重进 README 与 fixture（S02 §3 的乱码率/章节一致性/正文占比/书名作者匹配我同意），三个构造 fixture（完整/截断/乱码）断言排序。
- 只有一个候选时：自动选中并把分数写进 selection，不要求用户点。
- 用户可 `select --variant X` 手动覆盖；重选不重新下载。
- **中文小说的现实路径**：用户把已有 txt/epub 放进指定目录，`capture import <路径>` 后走同一套 parse/score/select。这条必须是"一等公民"，不是顺带支持——因为本机联网中文源不可用（§1），这是用户实际能用起来的唯一路径。

### 2.5 需求 1 验收草案（可直接写进任务卡）

1. `capture import` 两个版本 txt（一完整一截断/乱码）→ 评分排序正确，`selection.json` 指向完整版；`--variant` 可覆盖。
2. `capture search` 对 Gutenberg 返回候选（离线 fixture 每次跑；live 手动一次，结果贴 handoff）。
3. fixture epub 解析章数与预期一致；GBK/Big5 fixture 转 UTF-8 正确。
4. 批量 3 本书、其中 1 个 URL 失效：其余 2 本成功，退出码非 0 且汇总失败项。
5. 重跑同一命令：缓存命中，不重复下载，产物 sha 不变。
6. 所有网络测试默认跳过；skip 不算通过，live 结果必须附实际输出。

## 3. 需求 2：三处语义必须写死

### 3.1 1/3 规则的精确定义（同意 S01/S02，补边界）

设本段从第 s 章开始，目标字数 T；从 s 章起累计正文长度，找到累计首次 ≥ T 的位置落在第 k 章、偏移 `r = (T − 第 s..k−1 章累计长度) / 第 k 章正文长度`：

- `r > 1/3` → 第 k 章计入本段，本段 = [s..k]；下一段从 k+1 开始。
- `r ≤ 1/3`（**含恰等于 1/3**）→ 第 k 章不计入本段，本段 = [s..k−1]；下一段从 k 开始（见 3.2）。
- 落点恰在章边界（r=0 或整章刚好用完）→ 直接按边界处理，不触发 1/3 判断。
- 单章正文 > T：整章输出，本段只有这 1 章，不切章。
- 若按 r ≤ 1/3 会导致本段 0 章（如 s 章本身已超 T）→ 强制至少 1 章（本段 = [s..s]）。
- 目标小于首章剩余：同上。

必须配表驱动测试 ≥10 例：恰 1/3、1/3±1 字、章边界、单章超长、末段不足、T 小于单章、起始章非 1、连续两段衔接。

### 3.2 被舍弃章节的归属（必须新增裁决）

用户原话"舍弃该章"有两种读法：

- **A 顺延**：该章属于下一段，全书不丢字、不重复；多段拼起来是完整全书。
- **B 丢弃**：该章从所有段中消失，每段独立成片更"干净"，但长书会累计缺章。

我建议默认 **A**，理由：需求 2 的用途是把整本书切成多段给视频用，缺章会让观众断剧情；B 下每段都短一截，目标字数越短缺口越多。提供 `--drop-partial`（默认关）满足 B。若用户本意是 B，代价要在方案里写清。

### 3.3 字数口径与目标语义

- 计数字符：规范化后的正文汉字 + 标点 + 字母数字；**不计章节标题、空白、页眉页脚**；全半角统一。口径写进 README，配 fixture。
- `--target-chars` = 本段正文累计目标（不是全书累计）；段间默认不重叠；偏差由 1/3 规则决定（±1 章）。
- 另一模式 `--chapters-per-segment K` 直接按章数切（对应用户"5 分钟 10 章"的例子），不涉及 1/3；两种模式互斥。
- 段 id 用章节范围 `seg_c0001-0010`（同意 S02），但**加参数哈希**（见 §4.2），否则换 T 重跑会覆盖。
- 全书一次切完：`segment --work <id> --all --mode chars --target 8000`，幂等、可续跑，输出 `segments/index.json`（章节覆盖范围、无重叠、无缺口自检）。

### 3.4 验收草案

1. 表驱动 ≥10 例，含恰 1/3 与 ±1 字。
2. 覆盖自检：所有段章节范围首尾相接、并集 = [1..N]、无重叠、无缺口（A 策略）。
3. 单章超长整章保留；末段不足保留。
4. 同输入重跑：产物不新增、sha 不变（幂等）；改 T 重跑：旧产物保留、新目录出现（不覆盖）。
5. 缺 `chapters.json` 时明确报错并提示先跑第 1 步，不隐式回退。

## 4. 全局架构：同意的部分 + 两个补充

### 4.1 共识（记录，不再讨论）

产物契约 + JSON Schema 校验；CLI 优先、UI 只做壳；pipeline 为唯一串联实现；`common/` 只放契约/IO/子进程封装，import 边界测试固化；章节解析在第 1 步但拆独立子命令；进度 JSONL 契约；Windows 中文/`#` 路径全程列表参数。

### 4.2 补充一：artifact 版本化（现稿缺口）

`seg_c0001-0010` 由章节范围决定，但同一范围可以用不同 `target-chars`、不同 prompt、不同裁剪策略重跑。现稿没有版本维度 → 要么覆盖（违反"不覆盖"），要么目录名漂移导致 manifest 引用断。

建议：`artifact_id = <kind>:<scope>:<params_hash8>`，目录名同 id；`latest.json` 指针记录当前采用版本；UI 默认展示 latest，可切换历史。manifest 已有的 `params` 可按规范化 JSON 算 hash，可复现。

### 4.3 补充二：stage registry（避免第三份编排）

pipeline 和 UI 都要知道"第 2 步是哪个 CLI、吃什么 kind、产什么 kind、参数 schema 是什么"。如果 UI 硬编码一遍、pipeline 再写一遍，就是 S02 说的"两份编排"问题的变体。

建议：`pipeline/stages.yaml` 声明式登记每个 stage（id、包名、CLI 入口、input_kinds、output_kinds、参数 schema），pipeline 与 UI 都只读它。它是数据不是代码，不违反"common 不 import 功能包"的约束。

### 4.4 命名与目录

同意 S01 目录：`novel_capture/ chapter_segmenter/ script_writer/ voiceover/ video_composer/ ui/ pipeline/ common/`。用户要"按功能命名"，建议**目录英文短名 + README/UI 中文显示名**（Python 导入与命令行更稳），在方案里向用户说明一句即可，不必单独表决。

## 6. 端到端验收

### 6.1 E2E-A（离线、确定性、可自动跑）

固定样例：一本 30 章公版书（Gutenberg 下载后固化为 fixture）或构造的中文 30 章样例；音频用 ffmpeg `sine` 生成，视频素材用 `testsrc2` 生成。

链路：`import → parse → segment → script(mock) → voiceover import → video_composer`。

断言：

1. 每步 manifest 通过 JSON Schema；`inputs` 的 sha256 与实际文件一致。
2. 章节覆盖：所有段并集 = 全书、无重叠、无缺口（A 策略）。
3. 相似度：mock 文案三项指标在硬阈值内；照抄 fixture 必须 fail。
4. 视频：ffprobe 时长误差 ≤0.5s、含音视频流、分辨率/帧率符合参数；图片模式每张时长误差 ≤1 帧。
5. 断点续跑：中途 kill 后重跑从断点继续，已完成产物不重算（按输入 sha 跳过）。
6. 幂等：同参数整体重跑不产生新产物。
7. 路径：在含中文与 `#` 的临时目录完整跑一遍。
8. 进度 JSONL：UI 只读该文件展示阶段/进度，不解析人读日志。
9. 离线：自动测试期间阻断网络，live 调用不进自动套件。

### 6.2 E2E-B（手动 live，结果贴 handoff）

gutendex 检索 → 下载 epub → parse → segment → **真实 LLM 1 段** → 用户提供音频 → 合成视频。只做一次冒烟，记录实际输出与耗时；不写成自动化测试。

### 6.3 E2E-C（单模块独立）

每个功能包 `python -m <pkg>.cli --help` + 最小 fixture 跑通，证明"每个功能能单独运行并产出结果"。

### 6.4 不编造

任何"检索成功率/相似度/时长误差"结论必须附命令与输出；skip 注明"未验证"；网络与真实模型调用不得计入自动化通过数。
