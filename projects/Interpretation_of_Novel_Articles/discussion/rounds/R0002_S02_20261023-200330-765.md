# S02 第 2 轮：U1–U6 待确认项与验收边界的核对

## 0. 结论先行

   - **U3 的 CLI 后端必须降级标注**：我第 1 轮主张"CLI 作生产默认"，S01 反驳成立，我接受 HTTP 为生产默认；但 CLI 只能标 `experimental`、只能手动、不得作为任何验收通过依据。

2. 其余（robots、provenance 必填、三处版权文案一致、不打包 ffmpeg、preflight 门禁、中文用例离线为主）我无异议，只补验收细节，见 §7。

对方案的四条直接含义：

- **中文验收不必只靠自造样例**：Gutenberg 中文公版书可作为真实中文 fixture（繁体、120 回、回目可正则切分），它比"本地构造 30 章样例"更能验证第 1 步解析和第 2 步切章。这修正 S01 §3 的"中文用例只能来自本地 import"。
- **Gutenberg 正文必须剥离头尾样板文本**（`*** START OF ... ***` 前后），否则第一章会把许可证正文算进去，章节数、字数、1/3 规则全偏。S01 §2 的解析流程没写这条，验收要加 fixture 断言。
- **HTTP 客户端统一用 requests（已装），并显式设 UA**：不带 UA 直接 403；urllib 在本机会被链式自签证书挡住。**禁止 `verify=False`**——TLS 失败必须是结构化错误、可读提示，不能靠关校验"跑通"。
- **繁简**：简体书名检索不到中文书（实测 0）。要么提示用户用繁体/作者名，要么引入繁简转换（opencc 未装，需用户同意加依赖）。这是"关键词检索"可用性描述的一部分。

## 2. 对 U1 的实质异议：单 URL 提取与原需求的三个差距

S01 把 B 收窄为"用户逐个提供的 URL 单页正文提取"，方向我同意（不做站点适配器、不做检索、不绕墙）。但必须对用户讲清三件事：

### 2.1 单页 ≠ 全文（最大差距）

小说站普遍是"目录页 + 每章一页"。用户给一个正文 URL，通常只能拿到 1 章；S01 明确"不做站内链接发现"，所以 B 不能自动得到全书。原需求写的是"能获取网络资料并得到小说文本（txt 或 epub）"——在 B 下这句只对公版目录/本地文件成立，对普通 URL 不成立。

**建议写进 U1 提问正文**：「B 的 URL 路径是单页正文提取，通常为一章，不保证整本；整本捕获只对公版目录或本地文件成立。」

### 2.2 "关键词检索"和"多书名空格分隔"只对 Gutenberg 生效

原需求要"支持关键词检索""多个书名空格隔开、一次捕获多个资源"。在 B 下：

- 检索 = 只在 Gutenberg 目录内按书名/作者查；中文现代小说为 0 结果（合法源本来就不存在）。
- "多书名输入"只对 Gutenberg 检索成立；URL 路径的输入是 URL 列表，不是书名。

这不是实现细节，是**用户对需求 1 的预期**，必须让它显式可见，而不是等验收时才发现"输入《斗破苍穹》搜不到"。

### 2.3 多版本对比在 URL 路径上缺 work 绑定（内部可定，但影响验收）

用户给同一本书的 3 个 URL（3 个站/3 个版本），系统怎么知道它们属于同一本 work？S01 §2.1 的 provenance 没有这个字段。建议：

- `user_url` 与 `import` 都必须接受显式 `--work "书名" --author "作者"`；缺省时用页面 title 推断，但标 `work_binding=inferred`，**合并前必须用户确认**；
- 验收加一条：同一 work 的 3 个 URL → 3 个 variant + `selection.json` 排序正确；不同 work 不得误合并。

这是内部实现决定，不需要用户拍板，但漏了它，需求 1 的"多版本校验对比"就只有本地导入一条路能验收。

### 2.4 关于 `--urls-file`

S01 定义的是"逐条处理"，即每 URL 一个独立产物。若用户提供的是同一本小说的 20 个章节 URL，当前设计不会拼成一本书。**建议写死 P1 不做合并**；否则"多 URL 拼全书"会变成新的范围（排序、去重、断章续接、重复段落检测），应单列并让用户确认。这一点要在 U1 的回答里说明，避免用户以为给列表就能得全书。

## 3. 生产 HTTP / 可选 CLI：我接受 S01 的调整，但要加三条约束

我第 1 轮建议"本地 CLI 作生产默认"，S01 的反驳（登录态、配额、输出解析不可控）成立，**我放弃原主张**：生产默认 HTTP（OpenAI 兼容），测试 mock，CLI 可选。补充三点：

1. **CLI 必须降级为实验后端**：manifest 记 `backend=cli`，UI/README 标"实验性、仅手动"；自动套件与 E2E 不得以 CLI 通过作为验收依据。否则"CLI 也能跑"会被当成生产能力，而它依赖本机登录态，换机器就失效。
2. **三后端同一接口、同一录制 fixture**：切换后端不得改变产物 schema；HTTP 用本地 stub server 测请求构造/超时/重试/非 2xx 结构化错误（S01 已写，我同意）。
3. **供应商中立**：配置只有 `base_url` + `api_key_env` + `model`，不内置任何厂商默认值；未配置就报错，不做"猜测式默认"。

补两条 S01 没写的验收口径：

- **预算计数必须按 run 持久化**：调用次数写进 run 状态文件，断点续跑不得清零。验收加"超限中止 → kill → 续跑仍拒绝"，否则 resume 就是绕过预算的后门。
- **重试要有上限并记录**：网络重试不计"新调用"但要设上限（如 2 次），次数进 manifest。否则"每段 ≤2 次"在费用上不成立。
- U3 的选项应是**三态**：HTTP 真实联网 / 本地 CLI / 仅 mock。若用户选"仅 mock"，本期第 3 步不产出真实文案，方案必须写明，不能算未完成。

## 4. U4 第 4 步：与"配音先不写"的衔接（措辞必须改）

**不冲突**：导入不是合成，需求 4 说的"配音功能先不写"指的是 TTS。但三处要写死：

1. 第 4 步显示名不能叫"配音"，叫「外部音频导入（TTS 合成未实现）」；`voiceover synth` 明确返回未实现、非零退出、不产假音频（S01 已写，我同意）。
2. **不存在全自动 2→3→4→5**。准确表述是：2→3 自动；第 4 步是人工输入节点（用户提供 N 个音频）；4→5 自动。`--chain 2,3,4,5` 必须在第 4 步暂停等待输入，不能假装能跑通。S01 §6 的"pipeline 2→3→4→5 用导入音频跑通"建议改成这句，否则验收时会有人拿"全自动链"当标准。
3. **数量绑定**：第 3 步产出 M 段文案，第 4 步就需要 M 个音频；数量不符 → `needs_review` 或明确失败，**不能静默取第一个**。这条现在没写，验收要加。

两个依赖修正：

- **ffprobe 属于 ffmpeg 安装**，所以 U5 也阻塞 U4 的 mp3/m4a 时长探测。S01 §9 的"U5 阻塞 P4/P5 验收"应改为"U5 阻塞 U4 的 mp3/m4a 时长项与 P4/P5 验收"。
- 无 ffmpeg 时可先行的部分要写清：wav 用标准库 `wave` 取时长可离线验收；mp3/m4a 标 `duration_unverified`、skip 不算通过。这样 U4 的 manifest 完整性、坏文件拒绝、拒绝合成三类测试在无 ffmpeg 环境也能跑。
- 导入只读原文件（复制进库、不改不移动），坏文件/伪装扩展名 → `failed` + 可读原因，不落半成品。

## 5. U5 ffmpeg 表述的准确性

S01 §7 的方向（用户装系统 ffmpeg、不打包、不自动下载、preflight 门禁、未装则标未验证）我同意，补三点：

- `winget` 在本机存在（实测 PATH），所以 `winget install Gyan.FFmpeg` 的前提成立；但**不要只给一条安装路径**。给 winget / scoop / 手动 zip + 配置 `ffmpeg_path` 三条备选，避免 winget 源不可用时用户卡死。
- preflight 不得联网、不得自动下载；`ffmpeg_path` 命中后仍要检查编码器（精简版常缺 libx264）。
- 调用 ffmpeg 一律列表参数、不经 shell（工作区路径含中文与 `#`），验收在含中文+`#` 的临时目录跑一次。
- 同意"未安装期间相关测试 skip、handoff 写未验证、P4/P5 不得整体 pass"。

## 6. U6 中文路径：事实修正与"是否要拍板"

**事实修正**：S01 §3 的事实依据是"S04 实测维基文库不可达"，结论扩展成"中文走本地导入"。本轮实测显示：

- Gutenberg 中文目录可达（444 种），公版古典中文能合法联网获取，正文可切章（120 回）；这条可以成为真实中文 fixture 和中文 live 冒烟。
- **现代中文小说全部在版权期内，没有任何合法联网源**。用户大概率要的是这类书。这才是需求 1 的真实边界，比"维基文库连不上"重要得多。

因此：

- **U6 仍不需要单独选项**（同意 S01），但**不能只写 README 已知限制**。必须写进 U1 的提问正文和方案"已知限制"，让用户在批准方案时明确知道"现代中文小说不能联网捕获，只能本地导入或自己提供 URL"。否则用户批准的是他没看清的范围。
- 检索可用性：简体书名搜不到（实测 0），繁体能搜到（2 条）。要么提示用户用繁体/作者名，要么加繁简转换依赖（opencc 未装，需用户同意）——建议先用提示，不加依赖。
- 验收：中文 live 冒烟 ≥1 本 Gutenberg 中文书（手动，贴输出与书名）；自动测试用固化后的离线 fixture；不得写"支持中文维基文库"。

## 7. U2 文案（两条补充）

## 8. 内部可定 vs 需用户批准（建议总管据此写 decision）

**内部可定（直接写进方案，不问用户）**

- 二级身份、manifest 字段、artifact 版本化、UA、requests、禁用 `verify=False`、robots 必检、provenance 必填、Gutenberg 头尾剥离、繁简只做提示、wav 用标准库测时长、预算计数持久化、CLI 标 experimental、第 4 步人工节点措辞、第 4 步数量绑定。

**需用户批准（改变目标/范围/成本/环境）**

- U1：A/B/C（含"单页通常只有一章""现代中文无合法源"两句）。
- U2：接受"只承诺雷同度、不承诺不侵权"。
- U3：三态选择（HTTP / CLI / 仅 mock）+ 谁付费 + 预算上限 + 是否允许真实联网。
- U4：接受"第 4 步只做导入、TTS 不实现，且第 4 步是人工节点"这一范围定义。
- U5：是否愿意安装系统 ffmpeg（环境前提）。

**不单列**：U6 并入 U1 提问与方案已知限制；U7/U8 按默认值告知即可。

## 9. 推荐给用户的确认清单（措辞可直接用）

1. **U1（阻塞 P0 契约）**：需求 1 的联网捕获按哪种范围？A 仅本地导入 + 公版目录；B 在 A 上增加"用户提供的单个网页 URL 正文提取（通常为一章，不是整本；不检索、不站内遍历、不绕登录/付费墙）"；C 任意小说站关键词检索 + 批量抓全文（不建议，法律与工程风险需单独确认并书面承担）。注意：无论 A/B，**现代中文小说都没有合法联网源**；Gutenberg 中文目录可提供公版古典中文（本机实测可达，444 种）。
2. **U2（阻塞 P0）**：接受验收只写"雷同度低于阈值"，不写"不侵权"；免责声明随产物输出。
3. **U3（阻塞 P3 真实生成）**：三选一——HTTP（哪家、谁付费、单本预算）/ 本地 CLI（实验性，仅手动）/ 仅 mock（本期无真实文案）。
4. **U4（阻塞 P4 链路）**：接受"第 4 步只做外部音频导入，TTS 合成不实现；第 4 步是人工输入节点，不是全自动链"。
5. **U5（阻塞 U4 的 mp3/m4a 时长项与 P4/P5 验收）**：愿意安装系统 ffmpeg（winget/scoop/手动任选，项目不打包）。
